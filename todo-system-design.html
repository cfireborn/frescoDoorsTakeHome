Todo app: quick systems design

Users sign in, create and edit personal todos, mark them complete or incomplete, and receive a daily reminder of unfinished work. Todos initially appear oldest first. This is a design exercise, not an implemented app.

Scope and assumptions

Start with one private list per user and an optional daily email digest at their chosen local time. Email is an assumption because the reminder channel was not specified. Skip reminders when the list has no unfinished todos. Shared lists, recurring tasks, due dates, and mobile push can come later.

Technologies and architecture

Use TypeScript with Next.js for the web UI and HTTP API, managed PostgreSQL for durable data, Auth0 for login, and a transactional email service such as Amazon SES for reminders. Run a separate worker from the same codebase, awakened every minute by a managed scheduler. Begin with a single application and database; a separate cache or message broker is unnecessary at this scale.

Configure a small set of login choices, such as Google and email/password or email codes. Auth0 supports social, database, and passwordless connections; available methods depend on configuration. Keep credentials in the identity service. Map its stable issuer and subject to an internal user ID. Link additional login methods only after the user proves ownership of both accounts; matching email addresses alone must not merge accounts. See Auth0 identity providers.

Use secure, HttpOnly, SameSite session cookies over HTTPS, protect mutations against CSRF, and derive the user ID from the authenticated session. Every todo query includes that user ID, including updates and deletes. Validate text length, fetch lists in bounded batches, and rate-limit authentication and writes.

Database schema

IDs use UUIDs. Store absolute timestamps as PostgreSQL timestamptz.

users: id; reminder_email text nullable; reminder_email_verified_at timestamptz nullable; created_at timestamptz NOT NULL DEFAULT now(). Only send to a verified address, even when the login method does not supply one.

auth_identities: id; user_id UUID NOT NULL; issuer text NOT NULL; subject text NOT NULL; UNIQUE (issuer, subject). A user may have multiple identities without duplicating their todos.

todos: id; user_id UUID NOT NULL; title text NOT NULL with a nonblank, bounded-length constraint; completed_at timestamptz nullable; created_at timestamptz NOT NULL DEFAULT now(); updated_at timestamptz NOT NULL DEFAULT now(). A null completed_at means incomplete; setting it records completion, and clearing it reopens the todo. The application updates updated_at on each edit.

user_preferences: user_id UUID NOT NULL, one row per user; sort_mode text NOT NULL DEFAULT 'created_asc' with CHECK allowing 'created_asc' or 'created_desc'; reminder_enabled boolean NOT NULL DEFAULT false; reminder_local_time time without time zone NOT NULL DEFAULT '09:00'; timezone text NOT NULL DEFAULT 'UTC'; next_reminder_at timestamptz nullable. Validate timezone against IANA names. Recompute next_reminder_at when reminder settings change.

reminder_deliveries: id; user_id UUID NOT NULL; local_date date NOT NULL; scheduled_for timestamptz NOT NULL; status text NOT NULL with CHECK allowing 'pending', 'processing', 'sent', 'skipped', or 'failed'; attempts integer NOT NULL DEFAULT 0; retry_at timestamptz nullable; lease_until timestamptz nullable; sent_at timestamptz nullable; provider_message_id text nullable; UNIQUE (user_id, local_date). This durable job record supports retries and one daily digest per user.

Create an index on todos (user_id, created_at, id), a partial index on todos (user_id) WHERE completed_at IS NULL, and a partial index on user_preferences (next_reminder_at) WHERE reminder_enabled = true. Index reminder_deliveries (status, retry_at) for retry polling. These support stable list retrieval, unfinished-task lookups, and scheduling queries. See PostgreSQL multicolumn indexes and partial indexes.

API and ordering

GET /api/todos?cursor=… fetches the signed-in user's todos in batches; ordering for display happens in the browser. POST /api/todos creates one. PATCH /api/todos/:id edits its title or completion state. DELETE /api/todos/:id removes it. GET and PATCH /api/preferences read and save ordering and reminder settings. Return 404 for an ID the user does not own.

The browser loads the complete list, then sorts by created_at ascending, with id as a tie-breaker for identical timestamps. Switching to newest first reverses the client-side comparison. Keep created_at immutable so editing or completing an item does not move it. The API uses a fixed (created_at, id) cursor only for stable batch retrieval; changing the display sort does not change API queries. Wait until all batches are loaded before presenting the list as globally sorted, since sorting a single batch would give an incomplete order.

Persist the chosen sort_mode in user_preferences so it follows the user across devices. The frontend maps named modes to comparison functions; the backend validates and stores the preference. Future alphabetical or due-date ordering adds a client comparison and, for due dates, a new todo field. If users later need drag-and-drop ordering, add a separate position field then; creation time should retain its original meaning.

Daily reminder flow

Compute the next local occurrence from the user's time and timezone, then store its UTC instant. Use a timezone-aware library. Define daylight-saving behavior explicitly: move a nonexistent local time to the first valid time afterward, and use the first occurrence of a repeated time. The unique user/date constraint prevents a second reminder job that day.

Each minute, claim due preference rows in a short transaction using row locks and SKIP LOCKED. Insert a pending delivery with its local date, using the unique constraint to avoid duplicate jobs, and advance next_reminder_at to the next future local occurrence. After downtime, send at most one catch-up digest, rather than one for every missed day.

The worker claims a delivery with an expiring lease, then checks that reminders remain enabled and the recipient remains verified. Query incomplete todos immediately before sending; mark the delivery skipped if none remain. Commit the claim before calling the email service. Store successful delivery status and retry temporary failures with capped exponential backoff. Expired leases allow recovery after a worker crash.

Use the delivery ID as a provider idempotency key if supported. A crash after the provider accepts an email but before the database records success can otherwise cause a duplicate; exactly-once email delivery is not guaranteed. A todo completed immediately after the digest query may still appear in that email. Keep email contents minimal and link back to the authenticated list.

Future developments: millions of users

Scale from measured peak traffic, todos per user, and reminders due per minute. Run stateless application instances behind a load balancer, serve static assets through a CDN, and use database connection pooling. Keep client-side sorting for ordinary lists; very large personal histories need archives or filtered views so the browser does not download and sort years of todos on every visit.

Move reminder work to a durable queue with multiple workers, partition scheduling work, and publish jobs reliably from committed database records. Keep delivery deduplication and retries. Size capacity for popular reminder times: one million reminders due within a minute would require about 16,700 sends per second to stay within that minute. Throttle against the email provider's daily and per-second quotas, and monitor queue age, bounces, and delivery delays.

Tune indexes and queries first, archive old delivery records, and add read replicas for reads that can tolerate replication lag. If data growth warrants it, use table partitioning for maintenance; it does not distribute database writes across machines. If a single database becomes the measured bottleneck, shard by user_id so each user's todos and preferences stay together. Add load tests, failover drills, and capacity monitoring before relying on the design at that scale.

Tradeoffs and validation

Managed authentication reduces credential-handling work but adds provider dependence. PostgreSQL gives transactions, relational ownership, and durable jobs in one system. Minute-level polling means reminder timing is approximate and depends on worker and email-provider availability. Add a dedicated queue only when measured job volume or retry needs justify it.

Before shipping, test ownership isolation, identity linking, completion/reopening, equal-timestamp batch retrieval, client sorting across all batches, sort changes, timezone and daylight-saving transitions, empty lists, disabled reminders, concurrent workers, and crash/retry behavior. Monitor scheduler lag and failed deliveries without logging todo contents. Enable database backups and verify restores.
